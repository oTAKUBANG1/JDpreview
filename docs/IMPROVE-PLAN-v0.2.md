# 简历 × JD 对齐 Agent —— v0.2「改得好」改进方案

> 版本：v1（2026-11-05）｜状态：待评审
> 前置文档：`docs/PRD.md`（v0.1）、产品评审结论（定位/能力/闭环三类不足）
> 本方案回答一个问题：**在不放弃「不编造」底线的前提下，怎么把「改得好」从零做到可测、可验收。**

---

## 一、问题定义：把「改得好」拆成可测的三层

v0.1 的短板是用户可感知的改写幅度 ≈ 0（只重排 + 14 对同义词替换，strict 模式连替换都不做）。「改得好」不是一个模糊目标，拆成三层，每层有不同的验证手段：

| 层 | 内容 | v0.1 现状 | 验证方式 |
|---|---|---|---|
| L1 对齐层 | 术语统一、条目按 JD 权重重排 | ✅ 已有 | 现有五道闸门 |
| L2 表达层 | 句式重构、动宾强化、结果前置、信息密度提升 | ❌ 为零（明确不做自由改写） | **本方案核心**：编辑操作级验证 |
| L3 补全层 | 待补清单 → 用户口述回答 → 生成新条目 | ❌ 断裂（问题问了没有回路） | 来源标注 + 闸门复用 |

**核心矛盾**：L2/L3 必须引入 LLM，但 LLM 一进来，v0.1 的闸门就失效——五道校验全部基于字符串比对（`resume_text.includes(source)`），LLM 做任何同义改写后字符串就对不上，要么误杀（合理改写被判 BLOCK），要么形同虚设。**这不是「接个模型」的事，是闸门验证范式要跟着换。**

---

## 二、方案对比与选型

| 维度 | 方案 A：LLM 自由改写 + 事后闸门 | 方案 B：LLM 受限编辑（Edit-OP 协议） | 方案 C：双通道（规则 + LLM 并行，用户选） |
|---|---|---|---|
| 实现成本 | 低（改写器直接换模型） | 中（协议 + 闸门改造 + diff UI） | 低 |
| 开发复杂度 | 低 | 中 | 低 |
| 用户体验 | 好（句子真的变好了） | 好（同样变好，且每条可勾选） | 差（两版结果让人自己挑，决策负担在用户） |
| 风险 | **高：闸门失效，防幻觉底线失守** | 中：协议表达力需迭代 | 中：差异化没建立，等于两个半成品 |
| 上线时间 | 快 | 1–2 周 | 快 |

**选 B。理由：**
1. 方案 A 的风险是结构性的：字符串级溯源面对自由文本必然失效，「可验证」这个唯一差异点直接归零，等于变成又一个会编的 AI 润色工具；
2. 方案 B 把 LLM 的输出从「一篇改好的简历」变成「一组结构化编辑操作」，每个操作可以逐条机器验证——v0.1 攒下的闸门资产不报废，而是升级验证对象；
3. 方案 C 不解决任何问题，只是把不确定性转嫁给用户。

**B 的增强（B+，一并纳入本期）**：
- **用户逐条确认（Ask first）**：rephrase/merge 类操作默认不直接进稿，逐条展示「原文 → 改后」由用户勾选——采纳率同时成为「改得好」的量化指标；
- **本地模型优先**：简历是敏感个人信息，默认走本地 LLM（OpenAI 兼容接口，如本地部署的 DeepSeek），数据不出机器；云端模式须显式开关 + 告知。这本身是面向求职者的合规卖点。

## 三、核心设计：Edit-OP 协议

### 3.1 改写器输出契约（LLM 只准输出操作，不准输出成稿）

LLM 输入：行编号化的结构化简历（line_id）+ JD 能力清单 + 证据映射 + 约束卡。
LLM 输出：JSON 操作数组，操作类型为**封闭枚举**：

| OP 类型 | 参数 | 说明 | 用户确认策略 |
|---|---|---|---|
| `reorder` | line_id, to | 条目移动（沿用 v0.1 重排规则，标题行/日期行禁动） | Always（无需确认） |
| `term_align` | line_id, from, to | 术语对齐，仍受 14 对白名单约束（白名单需修错，见 6.3） | Always |
| `rephrase` | line_id, before, after, intent | 同一句内句式重构 | **Ask first** |
| `merge` | line_ids[], after | 相邻句合并提升信息密度 | **Ask first** |

**禁止的 OP（协议层直接拒绝）**：新增 line、删除 line、修改 header/公司/日期行。不在枚举里的任何输出按非法丢弃。

### 3.2 硬约束（写进提示词 + 闸门双保险）

1. **动词事实等级锁定**：建立动词等级表 `主导 > 独立负责 > 负责 > 参与 > 协助 > 支持`。改写后动词等级 ≤ 原文等级。v0.1 的 V2 升格检查保留，从「禁词表」升级为「等级表比对」。
2. **数字集合不变**：改写后句子的数字集合 ⊆ 原句数字集合（merge 则 ⊆ 各原句并集）。**新数字禁止**——量化挖掘只能从原简历其他行搬运数字到改后句，搬运也要过闸门。
3. **技术实体集合不变**：改写后实体 ⊆ 原句实体集合。
4. **意图标注**：每个 rephrase 必须带 intent（如「结果前置」「动宾强化」「去冗词」），用于人工抽检和反馈沉淀。

### 3.3 闸门改造（V1–V5 逐条对应）

| 检查 | v0.1 口径（字符串） | v0.2 口径（操作级） |
|---|---|---|
| V1 溯源 | `resume_text.includes(source)` | OP 的 line_id 必须存在于原简历；before 必须与原文该行一致 |
| V2 升格 | 强动词禁词表 | 动词等级表：after 等级 ≤ before 等级 |
| V3 数字/实体 | 字符串包含 | 数字集合、实体集合：after ⊆ before（merge 取并集） |
| V4 覆盖/贴标签 | 保留 | 保留，口径不变 |
| V5 缺失泄漏 | 保留 | 保留；L3 新条目走独立来源通道（见第五节） |

**关键收益**：合理改写不再被误杀（字符串变了但集合没变 → PASS），编造依然被拦（集合扩了 → fatal）。

### 3.4 流水线（复用 v0.1 编排）

```
JD 解析 ──► 证据匹配 ──► LLM 产出 Edit-OPs ──► OP 合法性校验（schema + 枚举）
                              │                     │
                              ▼                     ▼
                        用户逐条勾选 ──► 闸门（操作级 V1–V5）──► 采纳的 OP 应用成稿 ──► 交付
                              ▲                │
                              └── REVISE（带违规原因回炉，≤3 轮）── BLOCK → 回退原文
```

## 四、AI 专项六模块（按 AI 功能需求规范落实）

| 模块 | 本方案的落点 |
|---|---|
| 1. 任务定义 | 求职者贴 JD + 简历后，AI 帮到「草稿」级：给出每句的受限改写建议，用户逐条定稿。AI 不直接执行成稿（Ask first 层） |
| 2. 输入契约 | 结构化 line_id 简历 + JD 能力项 + 证据映射；简历含 PII，默认本地推理，不经网络 |
| 3. 输出契约 | Edit-OP JSON（schema 校验）；成稿由「已采纳 OP + 原文」确定性合成，LLM 永远不直接产出交付物 |
| 4. 质量标准 | 评测集 ≥30 个脱敏样本（含 6 个 v0.1 规格 + 诱导编造 + 长尾行业 JD）；阈值：**事实一致率 100%（硬门槛）、rephrase 采纳率 ≥60%（目标值，口径：用户勾选的 rephrase 数 / 展示的 rephrase 总数）** |
| 5. 异常降级 | LLM 不可达/超时/输出非法 → 降级为 v0.1 规则引擎行为（reorder + term_align），页面明示「当前为规则模式」；非法 OP 逐条丢弃不整批作废 |
| 6. 反馈闭环 | 每个 OP 记录 accepted/rejected + 拒绝原因（用户点选：升格了/不像我说的/没用/其他）；每月把高拒绝率的 intent 模式沉淀进提示词与评测集 |

**AI 行为约束三层**：
- **Always do**：reorder、term_align（机器可完全验证）
- **Ask first**：rephrase、merge（用户勾选后才进稿）
- **Never do**：产生新数字、新技术实体、提升动词等级、新增条目、改 header/日期行——无论用户怎么要求都不越过（用户想加内容走 L3 待补回路）

## 五、L3 回答回路（v0.3 预留，本期只留接口）

待补清单的追问 → 用户一句话回答 → 生成**新条目草稿**，与 Edit-OP 分通道：
- 新条目 `source_type: 'user_oral'`，Fact Ledger 记录用户原话，闸门对新条目只校验「不与原简历矛盾 + 不含 JD 强加的数字」；
- UI 上新条目用不同颜色标注「来自你的口述（YYYY-MM-DD）」，与原简历内容视觉区分。

本期动作：`missing_items` 数据结构已够用，不动；在 OP 协议里预留 `add_line`（本期禁用，v0.3 启用）。

## 六、配套修复（P0/P1，与 v0.2 并行或前置）

### 6.1 硬门槛比对（P0，半天，v0.1.2 先发）

- `parseResume` 提取学历、毕业年份推算工作年限；
- 与 `jd_json.hard_requirements` 逐条比对（学历就高不就低、年限按区间）；
- 结论规则新增一档：**硬门槛不满足 → 不建议投递（标注具体卡在哪条）**，优先级高于 must 缺口。
- v0.1 评审发现：`hard_requirements` 解析后无任何模块消费，这是「能不能投」结论的正当性缺口。

### 6.2 评分卡口径重建（P0）

| 问题 | 修复 |
|---|---|
| fact 一票否决在规则模式下恒 100（自证清白） | 事实一致率改为 **OP 级**口径（通过 OP / 总 OP），LLM 模式下才有区分度；规则模式下该维度直接不展示，不虚报 100 |
| jd_coverage 与 keyword_hit 共线（同一词库同一命中逻辑） | 合并为「JD 对齐度」单维度 |
| 权重 0.4/0.3/0.2/0.1 无依据 | 新权重随 v0.2 评测集校准，标注「校准前为默认值」 |

新打分卡（v0.2）：JD 对齐度（含 must 覆盖）+ 事实一致率（一票否决）+ 量化程度 + **改写采纳率**——采纳率是「改得好」的主指标。

### 6.3 词库与白名单修错（P1）

- `SpringBoot → Spring` 从 SAFE_ALIGN 移除（非等价替换）；
- 「支付/风控」从「金融」能力组拆出为独立能力（语义漂移）；
- missing 列表分流：「完全无经历」与「有经历缺量化」分开展示，行动指引不同（别投/补数字）。

## 七、验收标准（GWT）

| 编号 | Given / When / Then |
|---|---|
| T7 | Given LLM 模式 + 诱导编造样本（JD 要 5 年 AI 产品经历，简历没有），When 跑完整流水线，Then 改写稿无新数字/新实体/动词等级提升，该 must 项进待补清单 |
| T8 | Given 一条合理 rephrase（句式变了、数字实体集合不变），When 过闸门，Then PASS（v0.1 字符串口径下这是误杀） |
| T9 | Given LLM 服务不可达，When 分析，Then 自动降级规则引擎，页面显示「规则模式」，结果仍产出 |
| T10 | Given LLM 输出含非法 OP（如新增行），When OP 校验，Then 非法 OP 丢弃、合法 OP 照常应用，报告标注丢弃数 |
| T11 | Given 硬门槛「本科 + 3 年」与大专 1 年简历，When 分析，Then 结论=不建议投递，标注卡在学历与年限 |
| T12 | Given 30 样本评测集，When 全量回归，Then 事实一致率 100%，rephrase 采纳率 ≥60% |

评测集构建：以脱敏真实简历 + 真实 JD 为主（≥20 对），覆盖产品/数据/AI/技术岗 + 2 个长尾行业岗（暴露词库缺口）+ 全部边界用例。

## 八、风险登记册

| 编号 | 风险 | 类别 | 概率 | 影响 | 等级 | 应对 |
|---|---|---|---|---|---|---|
| RK-01 | LLM 幻觉绕过 OP 白名单（输出夹带成稿文本/非法操作） | 技术 | 4 | 5 | 20 高 | schema 硬校验 + 枚举外丢弃 + 闸门兜底三道防线；T10 验收 |
| RK-02 | OP 协议表达力不足，「改得好」仍不达预期 | 需求 | 3 | 4 | 12 中 | 采纳率监控；低于 40% 时按 intent 拒绝数据扩 OP 类型（一次只扩一种，附验收） |
| RK-03 | 本地小模型改写质量不够 | 技术 | 3 | 3 | 9 中 | OpenAI 兼容接口可插拔；本地/云端双通道，用户自选 |
| RK-04 | 简历 PII 经云端模型外泄 | 合规 | 2 | 5 | 10 中 | 默认本地推理；云端开关显式告知；日志不落简历原文 |
| RK-05 | 评测集样本不足导致阈值失真 | 数据 | 3 | 3 | 9 中 | 阈值标注「校准前默认值」；每月用反馈数据回补评测集 |
| RK-06 | 用户逐条勾选造成操作疲劳（30+ 条 rephrase） | 体验 | 3 | 3 | 9 中 | 默认折叠低分 OP；「全部采纳高置信」一键操作；每条勾选成本 <5 秒 |

## 九、版本规划

| 版本 | 范围 | 出口条件 |
|---|---|---|
| v0.1.2（先行，约半天–1 天） | 硬门槛比对 T11 + 评分卡共线修复 + SpringBoot/支付词库修错 | 现有 30 用例全绿 + T11 新增用例绿 |
| v0.2（1–2 周） | Edit-OP 协议、LLM 通道（本地优先）、逐条 diff 确认 UI、降级链路、OP 级闸门 | T7–T10 绿 + 10 样本冒烟 |

依赖就绪度：LLM 通道依赖本地模型或 API key（用户环境已具备本地 DeepSeek，分级=可绕过：不可达时降级规则模式）；无其他外部阻塞依赖。

## 十、遗留问题（不阻塞本期）

1. 分发形态（网页版/免安装）与商业模式仍未解决——技术改进不自动带来用户，建议 v0.2 验证采纳率后，用 10 个真实用户做假门测试再定投入；
2. 30 用例全为自造样本，评测集是第一次接触真实数据，预期会暴露词库与解析的一批新问题，预留一个修复迭代；
3. 中英混排简历、英文 JD 仍在范围外。
